# Відповіді 

## 1. Порушення обмежень у psql та їх аналіз

Для перевірки роботи обмежень у базі даних було навмисно виконано дві команди, які призвели до помилок:

* **Порушення обмеження CHECK (`ck_pt_priority`):**
  - **Команда:** 
    ```sql
    INSERT INTO product_tag (product_id, tag_id, priority) VALUES (1, 1, 15);
    ```
  - **Повідомлення PostgreSQL:** 
    ```text
    ERROR: new row for relation "product_tag" violates check constraint "ck_pt_priority"
    DETAIL: Failing row contains (1, 1, 15).
    ```
  - **Пояснення:** Перше речення повідомлення вказує на те, що рядок порушує конкретне правило перевірки з назвою `ck_pt_priority`. У блоці `DETAIL` СУБД показує значення вставленого рядка `(1, 1, 15)`, де `priority = 15` не відповідає умовам діапазону від 1 до 10, заданому в схемі.

* **Порушення зовнішнього ключа (`fk_pt_product`):**
  - **Команда:** 
    ```sql
    INSERT INTO product_tag (product_id, tag_id, priority) VALUES (999, 1, 5);
    ```
  - **Повідомлення PostgreSQL:**
    ```text
    ERROR: insert or update on table "product_tag" violates foreign key constraint "fk_pt_product"
    DETAIL: Key (product_id)=(999) is not present in table "product".
    ```
  - **Пояснення:** Ця помилка виникає через спробу вставити запис у дочірню таблицю `product_tag` із посиланням на неіснуючий `product_id = 999`. Повідомлення чітко інформує про порушення зовнішнього ключа `fk_pt_product`, а рядок `DETAIL` деталізує, якого саме батьківського ключа бракує в таблиці `product`.

## 2. Роль обмежень цілісності у Вашому варіанті

Усі обмеження, закладені в проєкті інтернет-магазину (варіант 23), виконують критичну роль у захисті даних від корекції чи внесення «сміття»:
1. **Первинні ключі (`PRIMARY KEY`)** гарантують унікальність кожної сутності (товарів, міток, категорій) та забороняють наявність значень `NULL` у ключових стовпцях, забезпечуючи надійну ідентифікацію рядків.
2. **Зовнішні ключі (`FOREIGN KEY` з `ON DELETE CASCADE` та `ON DELETE SET NULL`)** підтримують реляційну цілісність. Наприклад, каскадне видалення у сполучній таблиці `product_tag` автоматично видаляє зв'язки при видаленні товару чи мітки, запобігаючи виникненню «сирітських» записів. Самопосилання категорій з `ON DELETE SET NULL` дозволяє безпечно видаляти батьківські категорії, переводячи дочірні на рівень кореневих без видалення самих товарних категорій.
3. **Обмеження `CHECK`** захищають бізнес-логіку (наприклад, обмеження пріоритету мітки від 1 до 10 за допомогою `ck_pt_priority` або заборону категорії бути власним батьком за допомогою `ck_category_not_self`), що робить неможливим введення нелогічних чи помилкових даних.

Якби цих обмежень не існувало на рівні СУБД, база даних допускала б дублювання записів, посилання на неіснуючі товари, зациклення ієрархії категорій та порушення бізнес-правил, перекладання відповідальності за перевірку повністю на код програмного забезпечення, що незрівнянно менш надійно.

## 3. Труднощі під час роботи та їх подолання

Під час виконання практичної роботи першою складнощею стала синтаксична помилка створення таблиць (`42601 syntax error`), спричинена пропущеною комою під час перерахування стовпців та іменованих обмежень у таблиці `product_tag`. 

Повідомлення від PostgreSQL разом із виводом команди `python run_my.py` і термінала чітко вказали номер рядка та символ-покажчик (`^`), де сталася проблема. Це дозволило швидко локалізувати місце помилки, виправити синтаксис та успішно пройти всі автоматичні тести.
